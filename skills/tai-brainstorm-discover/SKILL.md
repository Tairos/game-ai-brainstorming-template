# Discover → Spark

Generate sparks: one-liners that kick off ideas. A spark can be an image, feeling, theme, contradiction, mechanic fragment, or “what if?”. It need not describe something playable or even something we can picture yet. Do not expand it into a pitch, core loop, rules, feasibility assessment, or prototype plan.

## Starting points

Use one or several starting sparks supplied in the request or unambiguously identified in the conversation. If none are available, ask for a starting spark or several and wait. Do not substitute your own starting point. A vague sentence is sufficient; do not turn it into a questionnaire or require a problem to solve.

Preserve the starting wording. When multiple sparks are supplied, explore them individually and combine them where interesting; do not silently collapse them into one premise. Respect explicit constraints, but do not import assumptions about genre, engine, budget, audience, or game-jam scope.

## Branching

Read [the technique menu](references/techniques.md) when generating sparks. Choose varied techniques that suit the input; do not mechanically apply every technique or force every spark into a gameplay mechanic. Include close associations and more distant departures when breadth is requested.

Branch from starting sparks and from generated sparks. Any descendant may become the next starting point. It is fine to lose the original thematic focus: ancestry records how an idea arose, not a requirement to justify it against the root. Combinations can have multiple parents.

Favor meaningfully different provocations over repeated wording or many cosmetic versions of one idea. Keep surprising or unresolved sparks; lack of a known implementation is not a reason to discard them. Do not rank a winner or move to Define without the user asking. Incorporate feedback without treating approval of a spark as approval of an entire game.

## Output

Match the requested number and branching depth. When unspecified, start with a manageable batch of about 8–12 new sparks; do not recursively expand without a stopping point.

Each spark’s creative content is exactly one sentence on one line. Use lightweight IDs and parent labels outside that sentence to make branches traceable, for example `S3 ← S1: A city that dreams only when its inhabitants disagree.` Use multiple parent IDs for combinations. Keep existing IDs when continuing an identified tree and avoid duplicates. Parent labels are bookkeeping, not extra pitch content.

A flat list with parent labels is usually enough; group by parent when it improves readability. Do not append an explanation, evaluation, or question to every spark. Technique names can be group labels when useful, but should not overwhelm the ideas.

Return sparks in the conversation by default. If asked to save or visualize them, preserve their one-line content and ancestry; use the shared [HTML map](../../assets/map.html) and [map format](../../assets/map-format.md) for a map. Do not create a recording workflow merely to generate sparks.
